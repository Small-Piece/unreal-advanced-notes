# 템플릿 패턴과 샌드박스 패턴

> 무기 시스템 같은 다형성 구조를 설계하는 두 가지 상반된 접근법. [[코드 스멜과 리팩토링]]에서 반복 스위치문을 다형성으로 해결하는 것의 발전형.

---

## 한 줄 비교

|패턴|핵심|누가 흐름을 짜나?|
|---|---|---|
|**템플릿 패턴**|흐름은 부모가, 세부는 자식이|C++ 프로그래머|
|**샌드박스 패턴**|도구는 부모가, 조립은 자식이|블루프린트 디자이너|

---

## 무기 시스템 상속 구조

```
AWeaponBase (기본 변수, Fire 딜레이)
    ├── ATemplateWeaponBase (발사 흐름 고정)
    │       ├── BP_Pistol (세부 구현)
    │       └── BP_Shotgun (세부 구현)
    └── ASandboxWeaponBase (도구만 제공)
            ├── BP_SandboxPistol (자유 조립)
            └── BP_SandboxShotgun (자유 조립)
```

## WeaponBase — 공통 기반

모든 무기가 공유하는 기본 변수와 발사 딜레이 처리:

```cpp
UPROPERTY(VisibleAnywhere, BlueprintReadOnly)
TObjectPtr<USceneComponent> Root;

UPROPERTY(VisibleAnywhere, BlueprintReadOnly)
TObjectPtr<UArrowComponent> FirePoint;

UPROPERTY(EditAnywhere, BlueprintReadWrite)
int32 AmmoPerFire = 1;

UPROPERTY(EditAnywhere, BlueprintReadWrite)
int32 MaxAmmo = 12;

UPROPERTY(EditAnywhere, BlueprintReadWrite)
float RoF = 1.f;        // Rate of Fire

UPROPERTY(EditAnywhere, BlueprintReadWrite)
float Range = 1000.f;

UPROPERTY(EditAnywhere, BlueprintReadWrite)
float DamagePerHit = 100.f;

UFUNCTION(BlueprintCallable)
virtual void Fire();     // 발사 후 딜레이 타이머 시작
```

Fire()는 `CanFire`를 false로 만들고, `1/RoF`초 후 다시 true로 복구하는 타이머를 건다.

## 템플릿 패턴 — "흐름은 내가 짤게, 세부만 채워"

### 핵심 아이디어

부모(TemplateWeaponBase)가 **발사 순서를 고정**하고, 세부 단계는 자식(블루프린트)에서 구현.

```
Fire() 호출
  → CheckAmmo()     // 탄약 확인 (BlueprintNativeEvent)
  → PlayEffects()   // 이펙트 재생 (BlueprintImplementableEvent)
  → ProcessFiring() // 발사 로직 (BlueprintImplementableEvent)
  → UpdateAmmo()    // 탄약 차감 (BlueprintNativeEvent)
  → Super::Fire()   // 딜레이 적용
```

### 코드

```cpp
void ATemplateWeaponBase::Fire()
{
    if (!CanFire) return;

    if (CheckAmmo())
    {
        PlayEffects();       // 블루프린트에서 구현
        ProcessFiring();     // 블루프린트에서 구현
        UpdateAmmo();        // C++ 기본 구현 있음, 블루프린트 오버라이드 가능
        Super::Fire();
        return;
    }

    Reload();
}
```

### BlueprintNativeEvent vs BlueprintImplementableEvent

|지정자|C++ 기본 구현|블루프린트 오버라이드|
|---|---|---|
|`BlueprintNativeEvent`|✅ `_Implementation()` 함수로|✅ 가능|
|`BlueprintImplementableEvent`|❌ 없음 (비어 있음)|✅ 블루프린트에서 구현|

- `CheckAmmo`, `UpdateAmmo` → `BlueprintNativeEvent` (C++에 기본 로직 있고, 필요하면 BP에서 재정의)
- `PlayEffects`, `ProcessFiring` → `BlueprintImplementableEvent` (C++은 빈 껍데기, BP에서 구현)

### 샷건은 뭐가 다른가?

권총과 거의 동일하되, ProcessFiring에서 **Trace를 여러 방향으로 쏘는 것**만 추가. 템플릿 패턴 덕분에 발사 흐름 코드는 건드리지 않고 세부만 바꿔주면 된다.

## 샌드박스 패턴 — "도구는 줄게, 알아서 조립해"

### 핵심 아이디어

부모(SandboxWeaponBase)가 **개별 기능을 BlueprintCallable로 제공**하고, 발사 순서는 블루프린트에서 자유롭게 조립.

```
Fire() 호출
  → SandboxFire()  // BlueprintImplementableEvent
                    // 블루프린트에서 자유롭게 조립:
                    //   CheckAmmo → LinetraceOneShot → PlaySound → UpdateAmmo
                    //   순서도, 조합도 디자이너 마음대로
```

### 코드

```cpp
// 흐름을 블루프린트에 완전 위임
void ASandboxWeaponBase::Fire()
{
    SandboxFire();  // BlueprintImplementableEvent → BP에서 구현
}

// 도구들을 BlueprintCallable로 제공
UFUNCTION(BlueprintCallable)
bool CheckAmmo();

UFUNCTION(BlueprintCallable)
void LinetraceOneShot(FVector Direction);

UFUNCTION(BlueprintCallable)
void PlaySound(USoundBase* Sound);

UFUNCTION(BlueprintCallable)
void UpdateAmmo();
```

### virtual + BlueprintImplementableEvent 충돌 문제

`Fire()`는 부모(WeaponBase)에서 `virtual`로 선언되어 있다. 그런데 `BlueprintImplementableEvent`은 내부적으로 자동 가상함수를 만들기 때문에 `virtual`과 **충돌**한다.

해결: Fire() 자체는 virtual override를 유지하되, 내부에서 별도의 `SandboxFire()`(BlueprintImplementableEvent)를 호출하는 **우회 방식** 사용.

```cpp
// Fire()는 virtual override 유지
virtual void Fire() override;

// 실제 BP 위임은 별도 함수로
UFUNCTION(BlueprintImplementableEvent)
void SandboxFire();
```

## 두 패턴 비교

|항목|템플릿 패턴|샌드박스 패턴|
|---|---|---|
|흐름 제어|C++가 고정|블루프린트가 자유|
|세부 구현|자식이 단계별로 채움|도구를 자유롭게 조합|
|확장성|흐름 내에서 변형|흐름 자체를 바꿀 수 있음|
|안전성|순서가 보장됨|디자이너 실수 가능성 있음|
|협업|프로그래머 주도|디자이너 주도|
|핵심 키워드|`BlueprintNativeEvent`|`BlueprintCallable`|
|Fire 함수|코드가 있음 (흐름 정의)|비어 있음 (BP에 위임)|
|추상 함수|세부 단계가 추상|Fire 자체가 추상|

> **서로 정반대**: 템플릿은 "코드 있는 함수→추상으로", 샌드박스는 "추상이던 함수→코드가 들어감"

## 언제 뭘 쓸까?

|상황|선택|
|---|---|
|발사 순서가 모든 무기에서 동일해야 할 때|템플릿 패턴|
|디자이너가 다양한 무기를 자유롭게 만들어야 할 때|샌드박스 패턴|
|프로토타입 단계에서 빠르게 실험할 때|샌드박스 패턴|
|버그 가능성을 줄이고 싶을 때|템플릿 패턴|
